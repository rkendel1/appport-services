# AppPort conformance corpus format, v1 (proposal)

This is a prototype, validated in `experiments/conformance-followup/corpus-v1/`. Its proposed home is the
protocol repository (`rkendel1/appport`), at `conformance/contracts/<corpus>/`. It is not a new package
or service.

## 1. What a corpus is

A corpus pins **one deterministic contract** to its **reference implementation**. Other implementations
(Rust, other TypeScript code, hosts) run the same inputs and compare their results at a declared level.
They may differ only where they say so, in writing.

| Corpus | Contract | Reference |
|---|---|---|
| `appport-ui-1` | `AppPort/ui/1` `validateUiContribution` / `filterUiContribution` | `@appport/protocol` |
| `capability-name-1` | names and `name@version` refs (spec §8) | `@appport/protocol` `validateName`, `parseCapabilityRef` |
| `webhook-signature-1` | outbound and inbound webhook signatures | `@appport/services` `src/webhooks/secrets.ts` |
| *(next)* `services-manifest-1` | `SERVICE_CAPABILITY_MANIFEST` and `serviceCapabilityManifestDigest()` | `@appport/services` |

## 2. Files per corpus

```
<corpus>/
  cases.json      human-authored, reviewed: inputs and intent, no outputs
  expected.json   generated by tools/bless.mjs from the reference only; reviewed as a diff
```

Consumers keep their own `narrowings.json` in their own repository (§6).

### 2.1 `cases.json`

```jsonc
{
  "contract": "AppPort/ui/1",
  "corpus": "appport-ui-1",
  "corpusVersion": "1.0.0",
  "operations": { "validate": "validateUiContribution(JSON.parse(input.json))", "...": "..." },
  "cases": [
    {
      "id": "ui1.route-dot-segments",
      "class": "security",
      "title": "route \"/ok/../../escape\"",
      "op": "validate",
      "input": { "json": "{…raw wire bytes…}" },
      "requirements": ["length-utf16-code-units"],
      "security": { "rationale": "why this case exists" },
      "referenceDefect": { "finding": "F-05", "summary": "…", "intended": { "verdict": "reject", "code": "INVALID_PROTOCOL", "field": null } },
      "decisionRequired": { "finding": "F-04b", "question": "…" }
    }
  ]
}
```

**Case fields:**

| Field | Rule |
|---|---|
| `id` | Stable and unique: `^[a-z0-9][a-z0-9.-]*$`. It **must not encode mutable attributes** such as the class or expected verdict, so a case can be reclassified without a rename. Prefix by corpus (`ui1.`, `name1.`, `wh1.`). Where readable slugs collide, add 6 hex of `sha256(input)`. |
| `class` | One of the five below. It records the author's intent, not the result. A class that disagrees with the reference's verdict is a review signal, not an error. |
| `input` | Holds the **raw wire form** (`json` as text, not a parsed value), so number spelling, duplicate keys, escapes and whitespace survive. |
| `requirements` | Tags that name the semantics a re-implementation must reproduce (`length-utf16-code-units`, `order-is-ecmascript-integer`, `no-unicode-normalization`, `first-error-wins-check-order`, `hmac-sha256-rfc2104`, `sign-raw-body-bytes`, …). |
| `security.rationale` | **Required** when `class` is `security`. `bless.mjs` refuses a security case without one. |
| `referenceDefect` | The reference's current output is still the blessed expectation, so nothing is relaxed silently. `intended` records the outcome a later reference release will produce. Consumers that already implement `intended` pass. |
| `decisionRequired` | Marks behaviour that is observed but not yet endorsed. It feeds the decision list. Its expectation is still the reference output until someone decides. |

**The five classes:**

| Class | Meaning |
|---|---|
| `valid` | Contract examples the reference accepts |
| `invalid` | Inputs that must be refused, with the expected error category |
| `boundary` | Limits and encoding: lengths in the contract's unit, Unicode, number spelling, wire quirks, scale |
| `security` | Regression cases for a security-relevant rule, with a rationale |
| `versioned` | Through `referenceDefect.intended`, plus the expected.json history (§4): explicitly versioned behaviour changes |

### 2.2 `expected.json`

```jsonc
{
  "contract": "appport-ui-1",
  "reference": { "package": "@appport/protocol", "version": "1.0.3" },
  "casesSha256": "…",   // binds expectations to the exact cases.json bytes
  "results": { "<id>": { "exact": "<JSON bytes of the result envelope>", "verdict": "accept|reject|internal", "code": "…|null", "field": "…|null" } },
  "history": [ { "at": "…", "reference": {…}, "reason": "…", "changed": [ids], "removed": [ids] } ]
}
```

- **Result envelope** (`exact`): `{ok:true,value}`, or `{ok:false,error:{code,message,details?}}` for a protocol
  error, or `{ok:false,internal:<JS error name>}` for anything else.
- Strings that a UTF-8 type cannot hold, such as lone surrogates, appear only inside `exact` as JSON escapes.
  This keeps the file loadable by `serde_json`.

## 3. Comparison levels

A consumer declares one level for the whole corpus.

| Level | Compares | For |
|---|---|---|
| `exact` | `exact` bytes | Bindings or ports that claim to be the same function (WASM/Node-API, another TS build) |
| `error` | verdict + `code` + `details.field` | Re-implementations that produce protocol errors but word messages differently |
| `verdict` | accept / reject / internal | Hosts with their own status model (Compute `service_ui`, AuthBoundry webhook verify) |

Messages are informative except at `exact`.

## 4. Generating and reviewing expectations

These are the only ways expectations change:

- **`node tools/bless.mjs <corpus> --check`**, the CI gate in the reference repository.
  - It regenerates every result from the reference.
  - It fails (exit 1) on any changed, removed or stale (`casesSha256`) expectation.
- **`node tools/bless.mjs <corpus> --write --accept=<id,…> --reason="…"`**, run by a maintainer.
  - It refuses (exit 2), writing nothing, unless **every** changed *and* removed id is listed in `--accept`.
  - It prints each unreviewed change as was/now.
  - It appends a history entry with the reference version and the reason.
- **No mode blesses an implementation under test.** Only `tools/references.mjs` produces results, and it
  loads only the reference package.
  - `APPPORT_PROTOCOL_DIST` can point the reference at a release candidate or a source build, to preview
    what a re-bless would change.
  - A preview is still a `--check`, so it writes nothing.
- **A reference fix for a `referenceDefect`** shows up as changed ids under `--check`. The maintainer
  accepts exactly those ids, removes the `referenceDefect` marker, and the history records it as a
  versioned change.

Validated (`results/review-gate.txt`):
- `--check` against the protocol source at `268c9b4`: pass.
- A mutated reference (max 511): `--check` exit 1, with the 3 changed ids named.
- `--write` without `--accept`: exit 2.
- `--write` with a partial `--accept`: exit 2.
- Renaming ids without listing the removed ones: exit 2.

## 5. Versioning

| Change | Version effect |
|---|---|
| Adding cases, or re-wording titles or rationale | Minor (`1.x`) |
| Any change to an existing expectation (a reference behaviour change) | Minor, with the history entry |
| The contract itself changing (e.g. `AppPort/ui/2`) | A **new corpus** (`appport-ui-2`). Old corpora remain for consumers of the old contract. |

The corpus version is independent of package versions. `expected.json.reference` records which package
version produced the expectations.

## 6. Consumers

Each consumer repository vendors `cases.json` and `expected.json` at a tagged corpus version, and keeps
a `narrowings.json` beside them:

```jsonc
{
  "consumer": "compute-environment service_ui::discover",
  "corpus": { "name": "appport-ui-1", "version": "1.0.0", "casesSha256": "…", "expectedSha256": "…" },
  "comparison": "verdict",
  "notApplicable": ["ui1.filter-…"],   // operations the consumer does not implement
  "narrowings": [ { "id": "ui1.route-dot-segments", "consumerVerdict": "reject", "kind": "host-policy|over-rejection|representation", "rationale": "…" } ]
}
```

The consumer test (`tools/consume.mjs`, ported to the consumer's language) **fails** on any of:
- an undeclared divergence;
- a declared narrowing that no longer diverges (stale);
- a narrowing for an id that is not in the corpus;
- a corpus whose checksums differ from the pinned ones.

All four were validated (`results/consumer-gate.txt`).

Narrowings may make a consumer **stricter** (`host-policy`) or document a **representation** limit.
A narrowing that makes a consumer **more lenient** than the reference is a contract violation:
- It needs an explicit decision record.
- It must not be used for `security` cases.

## 7. Distribution: vendored copies, pinned by checksum

**Recommended:** vendor and pin by checksum.
- Copy `<corpus>/{cases,expected}.json` from a tag of the protocol repository into the consumer, e.g.
  `compute/crates/compute-environment/tests/fixtures/appport-conformance/appport-ui-1@1.0.0/`.
- A ten-line sync script copies the files and writes the checksums into `narrowings.json`.
- Rust consumers read the JSON with `serde_json`. Nothing at test time needs Node, npm or network.

This is the pattern FeltDB's committed contract corpora already use. It is also what Compute does today
with `tests/fixtures/appport-ui/`, which is one-sided and unversioned.

**Rejected alternatives:**

| Alternative | Why rejected |
|---|---|
| An npm package `@appport/conformance` | A new published package. Rust CI would need npm to fetch it. |
| A git submodule | Clone and CI friction, with no benefit over a pinned copy. |
| Generating expectations in each consumer's CI | Every Rust CI would need Node plus the reference package, and generation would not be reviewed. |
| A central conformance service | No need demonstrated. |
